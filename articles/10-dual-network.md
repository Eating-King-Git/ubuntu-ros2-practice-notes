# Wi-Fi 上网、网线连接设备：Ubuntu 双网卡怎样各走各的？

作者：Eating-King-Git。根据本人操作记录与官方文档整理，含 AI 辅助写作和核查。整理日期：2026-11-21。

适用场景：Ubuntu 笔记本通过 Wi-Fi 上网，通过 USB 或 Type-C 有线网卡直连设备。我的实际设备是一台 A3 机械臂，转接网卡使用 ASIX AX88179A。本文保留真实排查过程，隐去设备地址和网卡标识。

## 1. 两张网卡可以同时使用吗？

可以。关键不是“只能保留一张网卡”，而是让不同目的地址走正确的线路。

这次的目标很简单：访问互联网继续使用 Wi-Fi；访问直连设备使用专用有线连接。设备连接只需要本地子网通信，因此给它配置静态地址，不设置互联网网关和 DNS，并禁止它提供默认路由。

```text
Ubuntu 笔记本
├─ Wi-Fi：互联网及原有上网配置
└─ Type-C 有线网卡：专用子网中的设备
```

默认路由可以理解为“找不到更具体路线时走的出口”。它不必属于每一张网卡。NetworkManager 的 `never-default` 就是禁止某个连接成为对应地址族的默认出口；IPv4 与 IPv6 是分别配置的。[NetworkManager 连接设置官方说明](https://networkmanager.dev/docs/api/latest/nm-settings-nmcli.html)

## 2. 插上网线后，第一步为什么不是 ping？

先确认系统看到了网卡、网卡是否有物理链路，以及连接配置是否激活。否则后面的失败很容易被误判成 SDK 问题。

可以先执行这些只读检查：

```bash
nmcli device status
nmcli connection show --active
ip -br address
ip route show default
```

第一条看设备状态，第二条看当前实际启用的连接，第三条看地址，第四条保留原来的默认出口信息。网卡接口名和连接配置名是两回事，操作前要对应清楚。[nmcli 官方手册](https://networkmanager.dev/docs/api/latest/nmcli.html)

我的历史记录中，有线网卡的 `carrier` 曾在 0 和 1 之间变化。它反映物理链路是否建立：线缆、转接头、对端供电等都可能影响它。后来用户确认曾拔插 Type-C 扩展坞，这就给掉线提供了具体解释；不是所有掉线都应归因于代理或软件。

## 3. 静态地址怎么填，才能不影响 Wi-Fi？

先从设备当前配置或可靠手册确认设备地址与掩码，再选择同一子网内、没有冲突的电脑地址。不能把网上教程里的地址直接照抄，更不能把设备自己的地址填到电脑上。

在 Ubuntu 的有线连接设置中，核对以下项目：

| 项目 | 本次直连场景的选择 | 原因 |
|---|---|---|
| IPv4 方法 | 手动 | 设备侧没有给电脑分配地址的已确认条件 |
| 电脑地址、前缀 | 与设备同子网且不冲突 | 让两端直接通信 |
| 网关 | 留空 | 这条连接不负责上网 |
| DNS | 留空 | 本次直接按设备地址访问 |
| 默认路由 | 禁止此连接提供 | 保留原上网出口 |

如果设备要求跨子网路由、DHCP 或特定网关，就不能套用这张表，需要按设备网络设计配置。这篇讲的是已经确认的专用直连场景。

我当时只修改专用有线连接，没有关闭 Wi-Fi、清空全部路由或重置整个网络。修改后重新对照默认路由，确认上网出口保持原状。图形界面不同版本的文字可能不同，用 `nmcli` 查询实际结果比只记按钮位置更可靠。

## 4. 配置看起来对，为什么还要查“去设备的路由”？

因为系统可能还有 VPN、TUN 或策略路由。禁止有线连接成为默认出口，并不保证去设备的流量必然走它。

本次真实遇到的情况是：最初设备已经可达，后来转接网卡被拔插，专用连接失活；再次检查时，去设备的路线竟然落到了 TUN 接口。检查流程在这里停止，没有继续把请求发往错误路径。

读者可以输入自己已核对的设备地址，再查询本机如何选路：

```bash
read -r -p '输入已确认的设备地址：' DEVICE_ADDR
ip route get "$DEVICE_ADDR"
```

看输出中的 `dev` 是否是专用有线接口，`src` 是否是它的电脑地址。这个命令是在查询内核选路，不会因此向设备发送数据包。[ip-route 上游手册](https://man7.org/linux/man-pages/man8/ip-route.8.html)

如果结果不对，继续读：

```bash
ip rule show
ip route show table all
```

这些输出可能包含私人网络信息，公开求助前应去敏。此时应先修复专用连接或分析相应策略，不要凭猜测删除所有路由。

## 5. 为什么浏览器能打开设备网页，还不能说 SDK 通了？

因为它们验证的是不同层。

| 检查层 | 通过能说明什么 | 还不能说明什么 |
|---|---|---|
| 网卡与链路 | 系统识别网卡、物理连接建立 | 地址与路由正确 |
| 本机选路 | 访问目标会走预期接口 | 对端会响应 |
| ping | 对端回应 ICMP | 应用端口正常 |
| TCP 端口 | 指定端口能建立连接 | 应用协议和版本兼容 |
| HTTP 页面 | 网页服务能回应 | SDK 的 WebSocket 服务可用 |
| 只读协议查询 | 一种特定请求收到有效响应 | 所有控制接口与运动正常 |

我的历史记录中，ping 3 次均收到回复，HTTP 返回 200，网页标题符合设备页面；随后分别确认了网页端口与 SDK 端口的 TCP 连接。这里只能按层累积证据，不能把 HTTP 200 当作机械臂开发完成。

反过来，ping 不回应也不能直接判定设备不存在，有些设备会限制 ICMP。应结合厂家允许的检查方式、路由和端口状态判断。

## 6. 这次掉线最终怎么恢复的？

先检查物理连接并重新激活原有专用配置，确认接口、地址和路由恢复；连续多次检查稳定后，才进行一次固定的版本查询。

那次查询通过 WebSocket 返回了软件版本 `1.0.260819`、设备类型和六轴信息。查询程序没有创建 SDK 控制对象，也没有执行初始化、使能或运动；前后状态记录保持未使能、空闲。它证明当时这条只读请求可用，不代表所有 SDK 功能都测完了。

后续还把专用连接设为自动连接，并绑定到对应转接网卡，方便拔插后恢复。自动连接优先级用于选择连接配置，不能代替路由检查，也不能保证线缆松动时永远在线。[NetworkManager 的自动连接属性](https://networkmanager.dev/docs/api/latest/nm-settings-nmcli.html)

对于读者，恢复后的顺序应保持一致：链路、地址、选路、允许的连通性检查、最后才是所需的应用协议。不要因为十分钟前成功过，就省掉拔插后的检查。

## 7. 要不要把设备地址加入代理排除列表？

这取决于实际使用的程序是否读代理配置。浏览器、curl、Python 库可能各有行为；`NO_PROXY` 一类设置只能影响遵守它的应用。

它不能修复内核把目标选到错误网卡的问题，也不能保证 TUN 模式会自动绕过设备子网。遇到“浏览器能访问、程序不能”时，分别检查应用代理和 `ip route get`，不要把两者混成一层。

我这次保留了原有 Wi-Fi 与 TUN 配置，通过针对专用有线连接的检查定位问题。没有证据支持为了连接局域网设备而把全机网络配置全部推倒重来。

## 8. 怎样记录，下一次插线就不必重新猜？

私下保存接口与连接配置的对应关系、设备网络参数、是否自动连接、默认出口以及一次成功检查的时间。公开文章只保留结构与结论，不需要贴出整段地址、MAC、连接 UUID 或 Wi-Fi 名称。

修改前记录专用配置，回退时也只还原这份配置。若后续另有设备共用该网卡，应重新确认子网与路由，不要沿用过期的“上次成功”。

本篇的完成标准是：Wi-Fi 仍能承担原上网任务，访问设备明确走专用有线接口，并有对应时间的应用层验证。之后进入 ROS 状态接入，还要单独检查程序启动的副作用。

## Linux 常用命令小板块

| 命令 | 用途 |
|---|---|
| `nmcli device status` | 看网卡是否被识别及连接状态 |
| `nmcli connection show --active` | 看实际启用的连接配置 |
| `ip -br address` | 简洁查看接口与地址 |
| `ip route show default` | 查看默认出口 |
| `ip route get "$DEVICE_ADDR"` | 查询访问已指定设备的实际路线 |
| `ip rule show` | 查看策略路由规则 |
| `ip route show table all` | 在普通路由表解释不了时检查其他表 |
