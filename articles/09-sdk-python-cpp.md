# 厂商 SDK 装不上、编译失败：Python 与 C++ 依赖排查实例

作者：Eating-King-Git。根据本人操作记录与官方文档整理，含 AI 辅助写作和核查。整理日期：2026-11-21。

适用背景：Ubuntu 22.04、ROS 2 Humble、Python 3.10，以及一套同时提供 Python 和 C++ 接口的 A3 机械臂 SDK。本文记录的是 2026 年 11 月的一次环境处理；版本号用于定位问题，不是要求所有读者照着降级。

## 1. SDK、ROS 和驱动，到底是什么关系？

SDK 是厂商提供的开发接口；ROS 提供节点、消息等协作机制；设备驱动解决硬件访问的一部分问题；控制器固件则运行在设备内部。它们有关联，但不是装了其中一个，另外几个就自动可用。

这次用到的 Python `carm` 通过 WebSocket 通信，C++ SDK 则提供动态库，ROS 示例在这些接口外面再包装消息收发。[厂商 carm_demo 仓库](https://github.com/cvte-robotics/carm_demo)

因此，排查时先回答三个问题：当前失败的是 Python 导入、C++ 编译链接，还是设备协议通信？使用的是哪个版本和哪份源码？错误发生在接触设备之前，还是连接之后？

我采用的顺序是：

```text
确认来源与版本 → Python 独立验证 → C++ 编译与依赖检查
→ ROS 包构建 → 另行验证设备连接
```

## 2. 为什么 Python 要用虚拟环境？

因为系统工具、ROS 的 apt 包和项目的 pip 包可能有不同要求。把所有库装进系统 Python，出问题后很难判断是谁改变了依赖。

我的项目使用 Python 3.10 虚拟环境，并开启 `--system-site-packages`，让它能够访问系统安装的 `rclpy`、`cv_bridge`。这是这套 ROS 项目的选择：它减少了重复安装，也意味着虚拟环境不是与系统包完全隔绝。[Python 3.10 venv 官方文档](https://docs.python.org/3.10/library/venv.html)

下面是**新的练习目录示例**，不是原项目的重建脚本：

```bash
mkdir -p ~/a3-practice
python3 -m venv --system-site-packages ~/a3-practice/.venv
source ~/a3-practice/.venv/bin/activate
python -m pip --version
```

先确认 `pip` 显示的路径属于这个虚拟环境，再按对应 SDK 官方说明安装。优先用 `python -m pip`，减少“用一个 Python 运行、用另一个 pip 安装”的混淆。不要为了某个项目替换 Ubuntu 的系统 Python，也不需要用 `sudo pip` 解决普通虚拟环境依赖。

## 3. Python 包装完以后，怎样验收？

我当时固定的主要版本包括：

| 包 | 历史版本 |
|---|---|
| carm | 0.1.20261116 |
| NumPy | 1.24.4 |
| OpenCV Python | 4.7.0.72 |
| Open3D | 0.19.0 |
| mmengine | 0.10.7 |

这些是当时能配合工作的组合，不代表各包的最新版本。后续记录中，依赖检查和离线检查通过，锁定清单没有变化。

在已激活的环境中，可以先做两项不接触机械臂的检查：

```bash
python -m pip check
python -c 'from importlib.metadata import version; print(version("carm"))'
```

第一条检查安装包声明的依赖关系；第二条读取包元数据，不创建控制对象。`pip check` 通过并不保证每个二进制扩展都能加载，更不能证明设备兼容；项目还应针对实际使用的库补充导入或离线测试。

保存版本清单有助于复现，但 `pip freeze` 本身不是完整环境备份：操作系统、Python 版本、系统库和厂商文件仍需另外记录。

## 4. C++ SDK 下载到了，为什么还要核对三种版本号？

这次最容易混淆的地方是：官方页面显示版本 `1.0.261112`，下载附件文件名包含 `1.0.261104`，包内 CMake 又声明 `1.0.1`。

这些数字确实不同，不能任选一个后把另外两个当成笔误删掉。我保留了页面日期、原始文件名、文件大小、SHA256、包内版本和源码提交，再给自己的安装目录起一个清楚的名字。这样下次报错时才能确定讨论的是同一份文件。

历史记录显示，官方入口迁移后取得了 Linux amd64 附件，完成 ZIP 完整性和路径检查；本文不重新分发该附件，下载与许可条件应以厂商页面为准。[厂商 SDK 官方仓库与当前下载指引](https://github.com/cvte-robotics/carm_demo#简介)

也要先核架构。amd64/x86-64 的库不能因为文件名相似就拿去给 ARM 主机使用；Python SDK 可以安装成功，也不代表同包内的 C++ 库适合当前机器。

## 5. `find_package` 找不到 SDK，是没有下载成功吗？

不一定。我遇到的是环境脚本把 `arm_control_sdk_DIR` 指到了 SDK 根目录，但实际 CMake 配置文件位于 `lib/cmake/arm_control_sdk`。

对于配置模式查找，`包名_DIR` 应指向包含对应配置文件的目录；它不是随便指到解压目录就行。[CMake 官方 find_package 说明](https://cmake.org/cmake/help/latest/command/find_package.html)

当时的处理是写独立环境加载脚本，指向实际配置目录，并按需加入库搜索路径，没有把一堆实验配置永久追加到 `.bashrc`。还检查了重复加载不会不断堆叠路径。

另一个小细节是空的 `LD_LIBRARY_PATH` 项可能把当前目录带入搜索路径。写环境脚本时要处理“原变量为空”的情况，不能机械拼接冒号。让配置只作用于当前项目终端，回退时也更清楚。

## 6. 缺 `libjsoncpp.so.1`，能把 `.so.25` 改名吗？

这次不能用改名掩盖问题。SDK 请求的是 `libjsoncpp.so.1`，Ubuntu Jammy 系统里提供的是 `libjsoncpp.so.25`。文件名中的主版本与二进制兼容约定有关，造一个软链接不会让接口自动兼容。

当时的做法是从 JsonCpp 官方 `1.7.4` 标签构建独立共享库，放在 SDK 的专用依赖目录中，不覆盖系统库。该上游版本生成所需的 SONAME，历史记录显示 **57 个 C++ 单元测试通过**，随后 SDK 与构建产物的动态依赖和符号重定位检查通过。[JsonCpp 1.7.4 官方源码](https://github.com/open-source-parsers/jsoncpp/tree/1.7.4)

这里需要保留一个未知：厂商生成原二进制时使用的精确 JsonCpp 版本，并没有仅凭这次修复得到独立确认。这个办法证明当前文件的检查通过，不能扩大为所有固件、所有 SDK 调用都兼容。

一般排查顺序应是：优先查官方配套依赖与支持环境，再确认需要的 SONAME 和架构；必要时隔离构建可追溯的兼容依赖。不要先改系统库，再寻找解释。

## 7. 库找到了，ROS 包为什么仍然编译失败？

接下来出现的是源码依赖声明问题：代码已经包含 `tf2/LinearMath` 和 `example_interfaces` 相关头文件，但构建文件与包清单没有完整声明依赖。

我当时只修改了 `CMakeLists.txt` 和 `package.xml`：补上相应 `find_package`、目标依赖和包清单声明，再重新构建。保留上游未使用参数警告，没有把“无任何警告”当作编译成功条件。

历史结果是单臂与双臂两个 ROS 节点都编译完成，包索引能够列出它们。源码基于固定的 carm_demo release 提交 `5e6e4a5bee16222194392c76a12836ba15cf5136`，补丁单独保留。这比直接在源码里多改几处、最后只记“修好了”更容易维护。

## 8. 编译通过后，为什么没有立刻运行示例？

因为“运行示例”可能有设备动作副作用。源码检查发现，相关控制节点的构造流程会执行 `set_ready()`；厂商示例也可能把连接、使能和运动连续放在一起。不能把它当成单纯查看版本的命令。[厂商示例与接口说明](https://github.com/cvte-robotics/carm_demo)

所以离线阶段做了一个最小链接检查：包含 SDK 头文件，引用 `is_connected` 成员符号，但不创建机械臂对象。随后检查 ELF 架构、动态依赖和未解析符号。**编译产物存在、动态链接通过、真机协议正常、运动验收通过，是四个不同结论。**

后续另有连接和状态反馈验证，但不能倒过来把离线构建阶段写成完成了所有真机测试。公开教程也不应为了演示“安装成功”默认启动会使能设备的节点。

## 9. 这次应该留下哪些文件？

保留五类信息就足够让下次排查有起点：来源和版本表、Python 依赖清单、C++ 独立依赖目录、最小源码补丁、带退出结果的构建与检查日志。

我还把 Python 与 C++ 环境分开加载，避免一次性混入所有路径。回退先关闭使用这些环境的终端，核对后再归档专用目录；不要为撤回一个 SDK 批量卸载系统依赖。

## Linux 常用命令小板块

以下文件命令中的路径，应由自己核对后替换为已确认可信的官方文件。

| 命令 | 用途 |
|---|---|
| `python -m pip check` | 检查 Python 包声明的依赖 |
| `python -m pip freeze --local` | 记录虚拟环境本地安装包 |
| `sha256sum 文件` | 记录文件身份，便于比较两次下载 |
| `file 动态库文件` | 查看 ELF、架构等基本信息 |
| `readelf -d 动态库文件` | 查看需要的共享库及 SONAME |
| `ldd -r 可信动态库文件` | 检查可信产物的依赖与重定位；不要用于不可信程序 |
| `ros2 pkg executables 包名` | 列出已被环境找到的 ROS 可执行程序 |
